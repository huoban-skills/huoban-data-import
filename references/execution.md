# 导入执行与回读

## 通道

`.xls/.xlsx/.csv` 只走 `hac table +import-file`，四阶段状态机：prepare → revise（可重复）→ confirm-config → apply。完整参数与 artifact 格式读 `huoban-table` 的 `references/shortcuts/import-file.md`，本页只说本 skill 关心的编排点。

本 skill 的导入方式固定为 `create`，只新增数据。用户要求更新或覆盖已有数据时，那是另一件事，转 `huoban-table` 处理，不在本 skill 里做。

执行前先确认目标表可用的导入方式：

```bash
hac table import-file-options --table '<表名或TABLE_ID>' --space '<工作区名或SPACE_ID>'
```

## 导入前的快照

`create` 不改目标表已有数据，目标表不用备份。真正要盯的是关联表。

基线在关联表补数完成之后、正式导入目标表之前采集，记录两组：

1. 目标表当前条数，用来核对增量。
2. 本次关联字段会指向的**每一张关联表**的当前条数。

关联表必须记条数，因为关联匹配不上时平台可能在关联表里新建数据，这是脏数据的主要来源。这个行为在 prepare 之后要从 `configuration_guide` / `preflight` 里核实清楚，如果确实会新建，必须在 confirm-config 之前处理掉，不要抱着"先导了再删"的想法提交。

## prepare 阶段的核对点

prepare 返回后停下，逐项核对再决定 revise 还是 confirm：

- **列映射逐列核对**：以 `auto_matches` 为准，不用本地推断的表头去覆盖。Excel 列名与目标表字段名不一致时，服务端可能漏匹配或匹配到相近的别的字段，所以每一列都要看一眼落在哪个字段上，不能只看有没有报错。**每次 prepare 都把 `auto_matches` 打印出来并留在执行记录里，源文件有几列就要对上几列，少一列不许往下走**；小批量补导也一样，最容易漏的恰恰是三五行的补数。
- **关联列的子字段**：关联字段的映射目标要选到补好的索引字段，可选范围看 `mapping_field_options`。选错子字段的表现是匹配率突然很低，或者匹配上了但指向的不是那一条。
- **不导入的列显式置空**：确定不导的列设 `target:null`，不要留着让服务端自动匹配到意料之外的字段。
- **默认值**：`create` 必须给出非空默认值 artifact，或明确传空 artifact 表示不设置。不要静默跳过。默认值只填新增行的空值。
- **preflight**：把里面的告警逐条读完再走下一步，不要因为不是 blocker 就跳过。

## 小样本测试

正式导入前先取 10 到 20 条正常数据（不是边界数据，边界数据留在清单里另外处理）走完整流程。

导完立刻回读，核对三件事：

1. 目标表条数增量是否等于样本条数。
2. 抽查两三条，关联字段指向的是不是正确的那一条数据，不是同名的另一条。
3. 每张关联表的条数有没有变化，变了就是被新建了数据，停下来查。

样本导入后不删除，直接作为正式数据的第一批。删除会在数据动态里留痕，也多一次误删风险。

## 正式导入与回读

按方案次序逐批导，每批导完做同样三项回读再进下一批。中途出现条数对不上或关联指错，立即停下，不要继续导后面的批次。

导入过程中断或状态未知时，转 `huoban-table` 的 `references/commands/import-task.md` 查任务状态，不要重新提交。

## 临时取消必填

关联表补数或补更新时，目标表其它必填字段（价格、单位、件装）源文件里没有，导入会被拦。处理成一个固定动作，不拆开做：读当前必填清单 → 取消 → 导入或更新 → 不论成败立即恢复 → 回读必填清单核对与取消前一致。每次都重新读当前清单，不复用上一次的字段列表；是否恢复、恢复成什么样在方案 2.2 里写明并经用户确认。

## 导入后复扫

全量核对通过后、收尾前，再做一次复扫：把**本批**新建的关联表记录与表里其它记录按评估阶段同一口径（`keys_similar`）比一遍，找出评估时漏掉的相似记录。评估靠源文件与快照比，复扫靠落库后的实际记录比，两次口径相同但对象不同，能兜住快照残缺、源文件写法怪异、名称错字这几类漏网。

```bash
# 关联表全量落 CSV（含 item_id、主键字段、对照字段、创建人、创建时间）后
python3 scripts/resweep.py --snapshot '<关联表快照CSV>' --key '药品名称,规格' \
  --mine-col 创建人 --mine '<导入账号>' --since-col 创建时间 --since '<本批开始日期>' \
  --aux '生产厂家（上市持有人）' --outdir '<待确认目录>' --label '药品'
```

复扫清单进方案 1.2 待确认；判「是同一个」的：本批导入记录的关联字段改指系统记录（`relink.py`），全表回读确认没有记录再指向本批新建的那条，再删掉它。清单清空才能收尾。

## 待判记录先删后补

疑似匹配里没裁决完的记录如果已经建进了关联表，业务员会在两条相似记录里选错。用户要求时可以先删：

1. 只删本批建的，删前把所有指向它们的导入记录备份成 JSON（记录 id、关联字段、被删记录 id 与主键值），备份进 `源文件/`。
2. 删后这些记录的关联字段为空，方案里写明数量与备份位置。
3. 回传后按判定回填：判「同一个」的改指系统记录；判「不是」的按原值重建（带上筛选涉及的字段与全部能带的列）再改指新记录。改指用 `relink.py`，逐条 update-item，每步落记录文件。

## 改动范围

所有清理、改指、删除只限**本批导入建的数据**；分几天导的同一批算一批，按导入账号与时间圈定。其他人建的记录，哪怕与本批重复、哪怕明显是错的，只列进方案给用户，不动。全量核对条数对不上时先按创建人拆开看，第三方在导入期间手工加的数据不算差异。

## 失败与误建的处理

- 导入失败的恢复动作以 `huoban-table` 的 `references/shortcuts/import-file.md` 错误回退一节为准，只在同一 import run 里恢复。
- 关联表里发现被误建的数据，列进待处理清单交用户确认后再处理，处理方式由用户定。
- 导入后要把一批已导入记录的关联字段改指到别的记录（如相似记录裁决后指回系统老记录）时，用 `scripts/relink.py`，底层是 `hac table update-item` 逐条改。`update-items-by-ids` 会把整条记录的必填一起校验，目标表其它必填字段为空的行会被拒；单条命令只校验提交的字段。只改本批导入建的记录。
